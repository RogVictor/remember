# SEO RitualGroup24

## Аудит

Проект использует Next.js App Router, Payload 3.91.0 и PostgreSQL. SEO-плагин Payload отсутствовал. Записи pages уже хранили seoTitle, seoDescription и ogImage. Динамический маршрут использовал заголовок, описание и canonical. Изображение, Open Graph, Twitter Card и JSON-LD в HTML не выводились. В services и products были поля заголовка и описания. Категории и информационные карточки ссылались на pages. Товары открываются в каталоге /products.

Фиксированные разделы задавали заголовки в Next.js. Общий layout устанавливал noindex/nofollow, robots.txt запрещал обход целиком. Sitemap перечислял фиксированные и опубликованные CMS-страницы и подставлял текущую дату. Хлебные крошки вели с раздела на главную. В Lexical уже существовали блоки каталога и формы обратного звонка. Медиатека требовала ALT. Публичные CMS-чтения используют динамический рендеринг, noStore() и дедупликацию в рамках запроса через React cache().

## Редактирование

- **Страницы → SEO** управляет посадочными и информационными страницами по /[slug]. В карточках услуг, категорий и материалов есть переход к связанной странице. Для услуг сохранены исторические SEO-поля.
- **SEO разделов** управляет главной, услугами, похоронами, товарами, ценами, информацией о компании, информационным разделом, FAQ, контактами и политикой. Для изменения HTML опубликуйте SEO-запись. При снятии этой записи с публикации раздел использует штатные значения.
- H1 на посадочной берётся из title. В фиксированных разделах H1 определён публичным шаблоном.

| Подраздел | Поля Payload |
| --- | --- |
| Основное | seoTitle, seoDescription, ogImage из media. Существующее ogImage служит основным SEO-изображением. |
| Семантика | focusKeyword, secondaryKeywords[].keyword, relatedKeywords[].keyword, searchIntent, targetRegions[].region, seoNotes. Варианты searchIntent — commercial, informational, transactional, navigational, mixed. Начальные регионы — Москва и Московская область. |
| Социальные сети | openGraph.title, openGraph.description, openGraph.image из media. Ориентир для изображения — 1200 × 630 px. |
| Техническое SEO | canonicalOverride, robots.index, robots.follow, schemaType. Флаги robots по умолчанию разрешены на уровне документа. Типы Schema — auto, WebPage, Service, OfferCatalog, Article, FAQPage. |
| SEO-анализ | Результаты текущей формы, проверка ALT из медиатеки и проверка совпадений по кнопкам. |

В media флаг decorative позволяет выводить изображение с пустым ALT. В настройках компании schemaOrganizationType выбирает Organization или подтверждённый FuneralHome. Массив serviceRegions[].region задаёт фактические регионы для Schema.org. Если список пуст, используется город компании.

Для `/about` запись **SEO разделов** также содержит секции страницы. Этот маршрут берёт H1 из опубликованного первого экрана, при его скрытии использует название раздела. Снятие всей записи `/about` с публикации возвращает HTTP 404 и исключает адрес из sitemap. Тип страницы в графе — AboutPage. [Инструкция редактора](../about/ADMIN.md)

## Приоритет и публикация

1. Для посадочных приоритет имеет опубликованная запись pages. Пустые title и description могут брать исторические значения услуги, если URL однозначно соответствует одной опубликованной услуге. Для фиксированных разделов используется опубликованная запись site-seo.
2. Резервный заголовок берётся из названия страницы или раздела. К резервному заголовку внутренних страниц добавляется компания. Явный SEO Title выводится в заданном виде. Для главной резерв — компания и город.
3. Описание посадочной берётся по порядку из опубликованной информационной карточки, краткого описания однозначной услуги, первой непустой строки Lexical и общего описания сайта. Для фиксированных разделов используется описание сайта. Open Graph и Twitter используют социальные поля с резервом в итоговых SEO-полях и ogImage. Тип Twitter Card зависит от наличия изображения.
4. Canonical берётся из проверенного абсолютного HTTP(S) URL или из фактического пути и SITE_URL / NEXT_PUBLIC_SITE_URL. Sitemap исключает URL, canonical которых отличается от собственного адреса. Дата берётся из updatedAt записи CMS. Для фиксированного раздела без SEO-записи дата опускается.
5. SEO_INDEXING_ENABLED=true включает индексацию. В остальных окружениях страницы получают noindex/nofollow, sitemap пуст и robots.txt запрещает обход. При включении admin и API закрыты правилами обхода. Admin также выдаёт noindex/nofollow. CMS-маршрут черновика отвечает 404. Административный просмотр защищён существующим доступом Payload. Посадочные, связанные только с неактивными категориями, исключаются из sitemap и получают noindex/nofollow.
6. Metadata и sitemap читают опубликованные данные при запросе. Публикация, изменение и снятие с публикации отражаются без таймера или дополнительного кеша. Черновые правки не меняют HTML опубликованной версии.

## Анализ и JSON-LD

Предпросмотр и счётчики обновляются по форме. Ориентиры Title 50–60 и Description 120–160 символов служат редакционными рекомендациями. Проверяются поля, H1, вхождение запроса, содержательный текст, H2/H3, внутренние ссылки, ALT, Social Image, canonical, robots и применимость Schema.org. При недостатке данных анализатор показывает нейтральный статус. Семантика проверяется на повторы после нормализации пробелов и регистра. Проверка совпадений по кнопке использует индекс focusKeywordKey, опубликованные документы и права текущего пользователя. Результат содержит публичные адреса и названия. Совпадение — повод проверить поисковые данные. Семантика доступна редакторам и не добавляется в публичный текст и метатеги.

Один JSON-LD граф включает Organization или FuneralHome, WebSite, WebPage, а для внутренних страниц BreadcrumbList. Тип посадочной определяется связями или настройкой редактора. Каталоги описывают видимые услуги и проверенные ссылки. Страница услуги ссылается на родительскую категорию и доступные услуги той же категории. FAQPage на FAQ и главной соответствует видимым вопросам и ответам аккордеона. Из CMS берутся название, логотип, город и фактические регионы компании. Цена, рейтинг, адрес, телефон и часы работы в разметку не включаются. [Schema.org OfferCatalog](https://schema.org/OfferCatalog)

## Контракт будущего импорта

[TypeScript-контракт](../../src/seo/import.ts) использует сгенерированные типы Payload. [Категория](category.example.json) и [услуга](service.example.json) содержат примеры JSON. Число 101 обозначает ID соответствующей категории. ID изображений подставляются из медиатеки. Технический ключ поиска рассчитывается при сохранении.

Для категории создать или сопоставить запись service-categories, подставить её ID в блок, создать посадочную и записать её ID в service-categories.page. Для услуги создать посадочную и записать её ID в services.page, а ID категории — в services.serviceCategory. Примеры задают статус черновика для проверки перед публикацией.

| Контент pages.content | Схема |
| --- | --- |
| Lexical | root.children[] содержит параграфы, заголовки, списки, ссылки и изображения. Формат узлов показан в примерах. |
| category-services | type = block, fields = { blockType: "category-services", category: ID }. Показывает услуги активной категории. Если на связанной посадочной нет этого блока, используется тот же раздел каталога. |
| callback-form | type = block, fields = { blockType: "callback-form" }. Использует действующую форму и URL страницы как источник заявки. |

## Миграция, развёртывание и откат

Миграция 20261124_162717_seo_module добавляет поля и индексы для pages, site-seo и версий, сохраняет старые столбцы SEO, инициализирует регионы существующих страниц и версий и расширяет настройки медиа и компании. Down удаляет данные новых полей, сохраняет старые SEO-данные и восстанавливает обязательный ALT. Для новых медиа с NULL в alt down подставляет пустую строку. [Миграции Payload](https://payloadcms.com/docs/database/migrations)

1. Зафиксировать предыдущий тег образа. В Bash создать резервную копию командой `docker compose exec -T db pg_dump -U payload -d funeral_site -Fc > before-seo.dump`. Проверить архив через `pg_restore -l before-seo.dump` и сохранить резервную копию тома медиа.
2. Собрать новый образ командой `docker compose build app`. Проверить миграцию на копии базы. Проверить статус командой `docker compose run --rm app npm run payload:migrate:status`.
3. В согласованное окно остановить запись в приложение, выполнить `docker compose run --rm app npm run payload:migrate`, затем `docker compose up -d app`. Проверить health, HTML страниц, robots.txt и sitemap.xml. Индексацию включать параметром окружения канонического сайта.
4. Для отката приложения вернуть предыдущий тег и перезапустить app. Для отката схемы сохранить актуальный дамп, остановить app и сверить, что последний пакет содержит только SEO-миграцию. Из нового образа выполнить `docker compose run --rm app node --experimental-strip-types --import=./scripts/payload-cli-loader.mjs ./node_modules/payload/bin.js --disable-transpile migrate:down`. Затем запустить предыдущий образ. Для восстановления из дампа сначала проверить pg_restore в отдельную базу и согласовать переключение.

В браузере проверены счётчик и изменение предпросмотра по форме, поиск совпадений и обе темы. Миграция up и down проверена на старой записи и версии.

### Ограничения

- Предпросмотр приблизительный. Формат выдачи и расширенные сниппеты определяет поисковая система.
- Проверка canonical оценивает синтаксис URL. Доступность внешнего адреса и смысловую эквивалентность проверяет редактор.
- Анализ шаблонов фиксированных разделов и динамических блоков ограничен данными CMS. ALT по ссылке на медиа проверяется отдельным действием. SEO товарного каталога управляется на уровне /products.
- Корневой ESLint отмечает существующую ошибку no-require-imports в tests/chat-telegram-fixture.cjs.
